# ADR-0003: Генерация только через OpenAI-совместимый контракт

**Статус:** Предложено
**Дата:** 2026-07-12
**Нужно до:** Фазы 3 (genclient)

## Контекст

Инструмент обязан работать с локальными моделями наравне с облачными — это принципиальная позиция проекта (хоумлаб, airgapped-сценарии) и практическое требование ниши: мастерская с лазером не обязана иметь API-ключ. Де-факто стандартом совместимости для локальных стеков стал OpenAI-совместимый chat-completions эндпоинт: его отдают llama.cpp, Ollama, vLLM, LM Studio и большинство облачных провайдеров или их шлюзы.

## Решение

`genclient` говорит ровно на одном протоколе: OpenAI-совместимый chat completions. Конфигурация — base URL, имя модели, опциональный ключ, температура и лимиты. Никаких провайдер-специфичных SDK, никакой собственной абстракции над «многими протоколами». Возможности за пределами общего знаменателя (структурированные выводы, специфичные параметры) не используются ядром — качество достигается промптом и петлёй, а не фичами конкретного API.

## Рассмотренные альтернативы

**Нативные SDK по провайдерам.** Доступ к фирменным возможностям. Отклонено: комбинаторика зависимостей, локальные стеки всё равно живут на совместимом эндпоинте. **Собственный слой абстракции над несколькими протоколами.** Отклонено как YAGNI: один протокол уже покрывает всё целевое множество; абстракция без второго конкретного случая — спекуляция.

## Последствия

Становится проще: одна кодовая дорожка, конфиг из трёх полей, честный оффлайн с локальной моделью, тесты через мок-сервер того же протокола. Становится сложнее: если появится провайдер с критичной возможностью вне стандарта, придётся решать отдельно — фиксируем как осознанный будущий ADR, а не тихое исключение. Пересмотреть: если экосистема сместится к другому стандарту совместимости.
