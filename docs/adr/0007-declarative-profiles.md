# ADR-0007: Профили — декларативные TOML-связки ограничений

**Статус:** Предложено
**Дата:** 2026-07-12
**Нужно до:** Фазы 4 (spec, promptsmith)

## Контекст

Ремесленное знание проекта — «какие ограничения делают вектор пригодным под конкретное производство» — должно жить в одном месте и питать сразу двоих: синтез промпта (что потребовать от модели) и валидацию (что проверить у результата). Если знание размазано по коду, ТЗ и проверка разъезжаются, и появляется худший класс багов: промпт требует одного, валидатор наказывает за другое.

## Решение

Профиль — декларативный TOML-файл: белые списки элементов и команд, топологические требования (замкнутость, число сабпутей), численные пороги (kerf и min-width, угол G1, ε флэттенизации), бюджеты (элементы, точность координат), включённые классы находок. Три встроенных профиля: `laser-cut`, `one-line`, `icon`. `spec` читает профиль и вшивает его в `VectorSpec` — единственный источник, из которого promptsmith формулирует, а validate проверяет; расхождение невозможно по построению. Пользовательские профили — просто ещё один TOML рядом, без изменения кода.

## Рассмотренные альтернативы

**Ограничения захардкожены в коде по профилям.** Быстрее старт. Отклонено: четвёртый профиль потребует релиза, знание нечитаемо снаружи. **Полноценный DSL с логикой.** Максимальная выразительность. Отклонено как overkill: связка «списки + пороги + флаги» покрывает все три целевых профиля; если однажды не хватит — это сигнал для нового ADR, а не для тихого усложнения формата.

## Последствия

Становится проще: профиль читается человеком как документация ремесла; добавление профиля — задача уровня pull request с одним файлом; тест профиля — прогон эталонных задач. Становится сложнее: схема TOML — публичный контракт с валидацией самого профиля при загрузке (внятные ошибки, не панки). Пересмотреть: набор порогов по умолчанию — после калибровки на живых резах (открытый вопрос ARCHITECTURE.md §13).
