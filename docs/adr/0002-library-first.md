# ADR-0002: Библиотека — ядро; CLI и MCP — тонкие адаптеры

**Статус:** Принято (подтверждено владельцем 2026-07-30)
**Дата:** 2026-07-12
**Нужно до:** Фазы 1 (задаёт форму workspace)

## Контекст

Целевая поверхность проекта — MCP-сервер: инструмент должен жить внутри агентских рабочих потоков. Но MCP-сервер неудобен как среда разработки ядра: отладка через хост, протокольный шум вокруг каждой итерации, привязка тестов к клиенту. Кроме того, у валидации есть самостоятельная жизнь вне агентов — pre-flight перед резкой, линтер в CI.

## Решение

Вся логика — в библиотечных крейтах, вызываемых без какой-либо поверхности. Поверхности — тонкие адаптеры без собственных знаний, появляются в порядке: CLI первым (Фазы 1–4 разрабатываются и тестируются через него), MCP — в Фазе 5, как зеркало CLI-команд. Инвариант: любой сценарий, доступный через MCP, воспроизводим через CLI один в один — это делает баг-репорты и учебные материалы независимыми от агентской обвязки.

## Рассмотренные альтернативы

**MCP-first.** Быстрее демо в агентском контексте. Отклонено: цикл разработки ядра становится заложником хоста, а самостоятельная ценность валидатора (линтер) откладывается. **Монолитный CLI без библиотечной границы.** Меньше церемоний на старте. Отклонено: MCP-слой потом пришлось бы выпиливать из бинаря, и граница «что публичный API, а что кишки» осталась бы непрочерченной.

## Последствия

Становится проще: тесты и golden-прогоны гоняются без протокола; ядро можно публиковать на crates.io отдельно от поверхностей; язык MCP-слоя (rmcp против TS-обёртки над CLI stdio) остаётся свободным выбором Фазы 5, потому что ядро от него не зависит по построению. Становится сложнее: дисциплина границы — поверхности не имеют права на логику, каждое исключение фиксируется ревью. Пересмотреть: при появлении третьей поверхности (например, web-плейграунд) — убедиться, что граница выдержала.
