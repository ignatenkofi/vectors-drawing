# ADR-0006: Валидация как структурированный отчёт с repair_hint

**Статус:** Предложено
**Дата:** 2026-07-12
**Нужно до:** Фазы 1 (report — первый крейт)

## Контекст

У результата валидации четыре разных потребителя: петля критики (нужны машиночитаемые правки для следующего раунда), человек за CLI (нужен внятный текст с координатами), агент за MCP (нужны структурированные данные), и golden-тесты (нужна стабильная сериализация). Булев ответ или свободный текст обслуживают в лучшем случае одного из четырёх.

## Решение

Единица результата — находка: `{code, severity, locus, message, repair_hint}`. `code` — из версионируемого словаря (`SELF_INTERSECT`, `G1_BREAK`, `OPEN_PATH`, …); `locus` — адрес с точностью до пути, сегмента, параметра t и координат; `message` — для человека; `repair_hint` — инструкция, написанная для модели: что именно и где починить, чего не трогать. Отчёт — список находок плюс метаданные прогона; сериализация JSON стабильна и снапшотится. Один и тот же отчёт без преобразований едет в петлю, в CLI-вывод, в MCP-ответ (как structured content) и в фикстуры. Действенные сообщения об ошибках MCP-инструментов — те же `repair_hint`, переиспользованные, а не отдельный механизм.

## Рассмотренные альтернативы

**Exit-code / булев результат.** Отклонено: петля слепнет, человек не видит «где». **Только человекочитаемый текст.** Отклонено: петля и тесты вынуждены парсить прозу. **Отдельные форматы под потребителей.** Отклонено: четыре представления одного факта неизбежно расходятся.

## Последствия

Становится проще: петля, линтер-режим, MCP и тесты питаются одним типом; словарь кодов — готовый учебный конспект дефектов векторной топологии. Становится сложнее: словарь и формат — публичный контракт, изменения только с версией; качество `repair_hint` требуется держать на уровне (см. ADR-0005). Пересмотреть: расширение locus для не-путевых находок (атрибуты, структура документа) — по мере появления таких проверок.
